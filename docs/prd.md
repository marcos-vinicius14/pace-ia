## 1. Executive Vision

**Pace AI** is an intelligent street running planning and coaching platform. Unlike generic plans, Pace AI uses Generative AI (LLMs) and RAG (Retrieval-Augmented Generation) to create personalized plans based on sports science, validated by real athlete data via **Strava** integration.

The project aims to demonstrate proficiency in:
- High-complexity software architecture.
- Data engineering (vectors).
- Cloud computing (AWS IaaS).
- Reactive full-stack development.

## 3. Software Architecture

### 3.1. Pattern: Vertical Slice + Clean Architecture
Code should be organized by business capabilities (e.g., `generate-plan`, `sync-strava`, `rag-coach`), clearly separating the Domain, Application, and Infrastructure layers.

### 3.2. Asynchronous Reactive Flow
1.  **Request:** User requests a plan via Vue.js.
2.  **Dispatch:** API sends a message to AWS SQS and returns ID (202 Accepted).
3.  **Processing:** Worker (EC2) consumes queue, invokes Spring AI.
4.  **Persistence:** Result saved in RDS (Relational + JSONB) and cached in Redis.
5.  **Notification:** SSE (Server-Sent Events) notifies the Frontend of completion.

### 3.3. Deployment Strategy (EC2 Auto Scaling)
- **Immutability:** Use of versioned Docker Images in AWS ECR.
- **Launch Template:** Defines `user_data` for automatic Docker Run.
- **Health Checks:** Spring Boot Actuator (`/actuator/health`) monitored by ALB.

## 4. Data Model (Schema)

### 4.1. Relational Tables (RDS PostgreSQL)

#### `athletes`
- `id` (UUID, PK)
- `strava_id` (BIGINT, Unique)
- `strava_access_token` (TEXT, Encrypted)
- `vdot_score` (DECIMAL) - Performance calculation.
- `max_heart_rate` (INTEGER)

#### `training_plans`
- `id` (UUID, PK)
- `athlete_id` (UUID, FK)
- `goal_distance` (ENUM: 5K, 10K, HM, MARATHON)
- `status` (ENUM: DRAFT, ACTIVE, COMPLETED)
- `ai_model_version` (VARCHAR)

#### `training_sessions` (The Calendar)
- `id` (UUID, PK)
- `plan_id` (UUID, FK)
- `scheduled_date` (DATE)
- `type` (ENUM: REST, EASY, INTERVAL, etc)
- `status` (ENUM: PENDING, COMPLETED, MISSED)
- `details_jsonb` (JSONB) - Rich workout content (warm-up, main set, etc).
- `strava_activity_id` (BIGINT) - Implicit FK for validation.

#### `strava_activities` (Audit)
- `id` (BIGINT, PK - Strava ID)
- `raw_data_jsonb` (JSONB) - Raw payload from Strava API.

### 4.2. Knowledge Base (RAG & pgvector)

#### `coaching_knowledge`
- `id` (UUID, PK)
- `content` (TEXT) - Excerpt from book/scientific article.
- `embedding` (vector(1536)) - Vector generated by OpenAI.
- `source` (VARCHAR) - E.g., "Jack Daniels Running Formula".
- **Index:** `ivfflat` using `vector_cosine_ops` for fast semantic search.

### 4.3. Cache Strategy (Redis)
- **Key:** `plan:{athlete_id}:{date}`
- **TTL:** 24 hours (for non-critical data) or 1 hour (for daily workout data).
- **Use:** Storage of SSE connection tokens and plan summaries for the Dashboard.

## 5. Features (Backlog)

### 5.1. AI Plan Generation (Core)
- **Input:** Target distance, race date, current level, available days per week.
- **Process:** Prompt Engineering + Domain Validation (15% volume rule).
- **Output:** Structured JSON saved in `training_sessions` and `details_jsonb`.
- **Tech:** SQS + Spring AI + WebFlux (SSE).

### 5.2. Interactive Dashboard (Vue.js)
- Monthly calendar visualization.
- Workout details on click (Modal).
- Status indicators (Completed, Pending, Missed).
- Real-time feedback during plan generation (SSE).

### 5.3. Strava Synchronization (2-Way Sync)
- **Import:** Strava Webhook triggers sync upon activity creation.
- **Validation:** Matching algorithm (Fuzzy Matching) between Strava date/distance and the daily plan.
- **Action:** Automatically marks session as `COMPLETED` if there is a match.
- **Handling:** Saves raw data in `strava_activities`.

### 5.4. Scientific Coach (RAG Feature)
- **Functionality:** "Ask the Coach" Chatbot.
- **Knowledge Base:** Physiology articles, classic training plans (Pfitzinger, Daniels).
- **Context:** RAG searches `pgvector` for relevant articles + athlete's recent history.
- **Output:** Science-based answers, not generic ones.

## 6. Business Rules & Domain

- **Safe Progression Rule (10-15%):**
  - The Domain (`TrainingPlan` entity) must calculate total weekly load.
  - If `week N > week N-1 * 1.15`, the plan must be rejected or AI instructed to recalculate. Fail-safe in Java layer.
- **Target Zones (VDOT):**
  - Training paces (Easy, Tempo, Interval) must be calculated mathematically based on the athlete's `vdot_score`, not just hardcodes.
- **Adaptive Feedback:**
  - If the user reports excessive fatigue, the system should suggest a "regeneration week" (Drop load) via AI.

## 10. Security Architecture

### 10.1. Authentication Strategy: Server-Side Session with Redis
To meet "High Engineering" requirements and maximum security, we will not use stateless JWTs on the client. We will use a distributed stateful session architecture.

**Concept:**
- **Client (Vue.js):** Only maintains a session identifier (Cookie).
- **Server (Spring Boot + Redis):** Maintains authentication state and access/refresh tokens in Redis memory (ElastiCache).

This ensures that even with multiple EC2 instances running (Auto Scaling Group), the user session is maintained and shared.

### 10.2. Security Stack
- **Framework:** Spring Security 6.
- **Session Management:** Spring Session Data Redis.
- **Transport:** Cookie HttpOnly, Secure (HTTPS), SameSite=Strict.
- **CSRF Protection:** Enabled and customized to work with SPA (Vue.js).
- **CORS:** Configured for the Frontend domain.

### 10.3. Authentication Flow (Login)
1.  **Request:** User sends username and password (via HTTPS) to endpoint `/api/auth/login`.
2.  **Validation:** Spring Security authenticates against PostgreSQL (`athletes` table).
3.  **Session Creation:**
    - If successful, Spring creates a new session.
    - Stores session data (including Authorities/Roles) in AWS ElastiCache (Redis).
    - Redis key will be something like `spring:session:sessions:<session-id>`.
4.  **Response:**
    - Server sends `Set-Cookie` header.
    - Cookie Name: `PACE_SESSION_ID` (renamed standard `JSESSIONID`).
    - Attributes: `HttpOnly=true`, `Secure=true` (prevents JS from reading), `SameSite=Strict`.
    - Body: Empty JSON or basic user object (no sensitive data).

### 10.4. Refresh Token & Access Token (Server-Side)
Although we don't send JWTs to the client, internally the server may use a short/long duration pattern to manage the session in Redis.

- **Access Logic (Primary Session):** The cookie points to the active session in Redis. We configure `maxInactiveInterval` to 30 minutes (example). If the user is idle, the session expires and they need to log in again.
- **Refresh Logic ("Remember Me"):** We can implement a secondary remember-me cookie (also HttpOnly) or store a refresh token in session attributes with a longer TTL (7 days). When the main session expires, the refresh filter can automatically restore it.

For this portfolio, we will keep it robustly simple: Redis Session with activity-based expiration.

### 10.5. RBAC (Role-Based Access Control)
Definition of roles and their access.

#### `roles` Table (Mapped in DB)
```sql
CREATE TABLE roles (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    name VARCHAR(50) UNIQUE NOT NULL -- 'ATHLETE', 'ADMIN'
);

CREATE TABLE athlete_roles (
    athlete_id UUID REFERENCES athletes(id),
    role_id UUID REFERENCES roles(id),
    PRIMARY KEY (athlete_id, role_id)
);
```

#### Permission Definition
- **ROLE_ATHLETE (Default):**
  - `plan:read`: View custom plans.
  - `plan:create`: Request new plans.
  - `activity:write`: Import/Sync Strava.
  - `chat:ask`: Ask the RAG Coach.
- **ROLE_ADMIN:**
  - `admin:logs`: View error and audit logs.
  - `system:monitor`: View application health metrics.

## 11. Technical Architecture: Hexagonal & Vertical Slices
The Pace AI project adopts an architecture that strictly separates Pure Domain (business rules that don't change) from Infrastructure (details that always change: database, external APIs, queues).

### 11.1. Fundamental Concepts
- **Clean Architecture / Hexagonal:** Code is organized in concentric circles. The core (Domain) knows nothing about Spring, AWS, or Databases.
- **Multi-Module Maven:** The project is divided into logical modules to force dependency separation via `pom.xml`. The Domain module cannot import classes from Spring or JPA.
- **Vertical Slice (Fatjar Organization):** Within "Use Case" or "Controller" modules, we group code by functionality (e.g., `generate_plan`, `sync_strava`) instead of by layer (e.g., controllers, services). This facilitates maintenance.

### 11.2. Internal Data Flow
1.  **Adapter-In (REST/SSE):** Receives the request (`GeneratePlanRequest`).
2.  **Application Layer:** Finds the corresponding Use Case (`GeneratePlanService`). Orchestrates the flow.
3.  **Domain Layer:** Executes calculations (VDOT, Zones), validates rules (15% volume), and defines immutable entities.
4.  **Adapter-Out (Infrastructure):**
    - The Use Case calls an Interface (Port) `PlanRepository`.
    - A concrete implementation `PostgresPlanRepository` saves to RDS.
    - An implementation `SQSMessagePublisher` sends to the queue.

## 13. Detailed Module Explanation

### 13.1. `pace-ai-domain` (Immutable Core)
This module MUST NOT have Spring Framework (`org.springframework`) dependencies.

- **Purpose:** Contain the business truth.
- **Content:** Rich Entities (e.g., `TrainingPlan.calculateWeeklyLoad()`), Value Objects (`Pace`, `Distance`, `HeartRate`), and Repository Interfaces (Ports).
- **Testability:** 100% testable without loading Spring context, just pure JUnit 5.

### 13.2. `pace-ai-application` (Use Cases)
Contains orchestration logic. It doesn't know how data is saved, only which port to use.

- **Dependencies:** Only `pace-ai-domain`.
- **Purpose:** Implements Services that control the flow: Receives DTO, calls Domain, updates Entity, calls Repository.
- **Example:** `GeneratePlanUseCase` which receives user data, invokes `AIGateway` (interface), and then persists via `PlanRepository` (interface).

### 13.3. `pace-ai-infrastructure` (Adapters)
Here lives the "dirty" code that depends on external libraries.

- **Dependencies:** Spring Data JPA, Spring Cloud AWS, Redis Client, etc.
- **Purpose:** Implements interfaces defined in Domain (Ports).
  - `PostgresPlanRepository` implements `PlanRepository`.
  - `SqsPublisher` implements `EventPublisher`.
  - **Mappers:** Converts `JPAEntity` (annotated with `@Entity`) to `DomainEntity` (pure).

### 13.4. `pace-ai-web` (Presentation)
The thin layer of contact with the outside world.

- **Dependencies:** `pace-ai-application`, `Spring Web`.
- **Purpose:** Exposes REST Endpoints and manages Security context.
- **Validation:** Receives DTOs (`@Valid`) and delegates to Application layer.

### 13.5. `pace-ai-startup` (Orchestrator)
The module that generates the final executable JAR.

- **Function:** Imports `@SpringBootApplication`, configures component scan, and unites all modules.
- **Configuration:** Defines which profile to use (local, dev, prod).

## 14. Naming & Code Best Practices
To maintain consistency between Hexagonal Architecture and implementation:

- **Package Names:** Use Feature name followed by Responsibility.
  - Ex: `com.paceai.infrastructure.messaging.sqs` and not `com.paceai.sqs`.
- **Interfaces in Domain:** Interfaces stay in the domain module. Ex: `PlanRepository`.
- **Implementations in Infra:** Implementations stay in infrastructure. Ex: `PostgresPlanRepository` or `S3PlanRepository`.
- **Clean Architecture:** No class from the infrastructure module can be imported by the domain module.
